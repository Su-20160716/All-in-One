## 二、P0 级（5 项）

### P0-1 刷新令牌恒失败：全员 12 小时后被迫重登 ✅已修复

**位置**：`backend/accounts/serializers.py:44-52`

```python
def validate(self, attrs):
    refresh = attrs["refresh"]                      # ← 这是 str，不是 Token 对象
    try:
        user = User.objects.filter(id=refresh.get("user_id")).first()
    except Exception:                               # ← AttributeError 被吞
        user = None
    if user is None or refresh.get("tv") != user.token_version:
        raise InvalidToken("登录态已失效，请重新登录")
```

**根因**：`rest_framework_simplejwt` 的 `TokenRefreshSerializer.refresh` 是 `serializers.CharField()`，`attrs["refresh"]` 是普通字符串，没有 `.get()`。抛出的 `AttributeError` 被 `except Exception` 吃掉 → `user=None` → 无条件 `InvalidToken`。

**实测**：用 `RefreshToken.for_user(admin)` 生成带 `tv` 的合法令牌，调用 `validate()` → `InvalidToken: 登录态已失效，请重新登录`。

**修复**：先解析成 `RefreshToken` 再读 claim，并收窄异常类型。

```python
def validate(self, attrs):
    try:
        token = RefreshToken(attrs["refresh"])      # 验签 + 验过期
    except TokenError as exc:
        raise InvalidToken(str(exc))
    user = User.objects.filter(id=token.get("user_id")).first()
    if user is None or token.get("tv") != user.token_version:
        raise InvalidToken("登录态已失效，请重新登录")
    return super().validate(attrs)
```

**回归验证**：合法 refresh → 成功签发 access；`tv` 不匹配 → 仍被拒（改密踢下线特性保留）；乱码 refresh → `InvalidToken` 而非 500。

### P0-2 操作日志把明文口令落库 ✅已修复

**位置**：`backend/core/middleware.py:30`、`:186-194`

**根因**：`SKIP_PREFIXES` 只挡了 `/api/auth/token|refresh|verify`，而真实口令接口是 `/api/auth/profile/change-password/`、`/api/auth/admin/users/<pk>/reset-password/`、`/api/auth/profile/deactivate/`。中间件把 JSON body 前 8 个键原样拼进 `OperationLog.detail`，管理员通过 `GET /api/core/logs/` 即可读到全站明文密码。

**修复**：补白名单 + 键名脱敏双保险。

```python
SKIP_PREFIXES = (
    "/admin", "/static", "/media",
    "/api/auth/token", "/api/auth/refresh", "/api/auth/verify", "/api/auth/login",
    "/api/auth/profile/change-password",
    "/api/auth/profile/deactivate",
    "/api/auth/profile/2fa",
    "/api/auth/admin/users",
)

_SENSITIVE_KEY_HINTS = ("password", "passwd", "secret", "token", "credential",
                        "totp", "otp_code", "verify_code", "captcha")

def _safe_detail(body: dict) -> str:
    parts = []
    for k, v in list(body.items())[:8]:
        low = str(k).lower()
        if any(h in low for h in _SENSITIVE_KEY_HINTS):
            parts.append(f"{k}: ***")
        else:
            parts.append(f"{k}: {str(v)[:40]}")
    return "{" + ", ".join(parts) + "}"
```

**验证**：`_safe_detail({'old_password':..., 'new_password':..., 'token':...})` → 三个值全部打码，普通字段正常保留。

### P0-3 全站 63 处 `:show` 弹窗静默失效 ✅已修复

**位置**：`frontend/src/components/Modal.vue:24-34`

```js
props: { show: Boolean, modelValue: Boolean, ... }
const visible = computed(() => props.modelValue ?? props.show)
```

**根因**：Vue 3 对 Boolean 类型的 prop，**未传时自动强转成 `false`**（不是 `undefined`）。于是 `false ?? props.show` 恒为 `false`。

**实测**（Vue 3.5.42 真实运行时）：

| 传参 | 修复前 | 修复后 |
|------|--------|--------|
| `:show="true"` | `HIDDEN` ❌ | `VISIBLE` ✅ |
| `v-model="true"` | `VISIBLE` | `VISIBLE` |
| `:show="true" modelValue=false` | `HIDDEN` | `HIDDEN`（modelValue 优先，符合设计）|

**影响面**：`grep "<Modal" | grep ":show"` 共 **63 处**——新建文件夹、分享、预览、备注、移动、批量重命名、发起聊天、转发、群管理、笔记模板/大纲/导入、看板新建卡片、TODO/洞察面板……全部点了没反应。仅 CodeForge 里 6 处用 `v-model` 的正常，所以症状是"部分弹窗好用、大部分失灵"，极难定位。

**修复**：显式 `default: undefined`，让 `??` 真正回落到 `show`。

```js
props: {
  show: { type: Boolean, default: false },
  modelValue: { type: Boolean, default: undefined },   // 关键
```

### P0-4 网段计算把整段地址物化，`/8` 直接 OOM ✅已修复

**位置**：`backend/devtools/views_misc.py:28`

```python
hosts = list(net.hosts()) if net.num_addresses > 2 else []
"first_host": str(hosts[0]) if hosts else str(net.network_address),
"last_host":  str(hosts[-1]) if hosts else str(net.broadcast_address),
```

```python
total = net.num_addresses

else:
    first, last = net.network_address, net.broadcast_address
# 另加护栏：if net.prefixlen < 8: raise ValueError("网段过大，请用 /8 及更具体的前缀")
```

### P0-5 日期序列在「步长为 7 倍数 + 只取工作日」时死循环 ✅已修复

**位置**：`backend/devtools/views_math.py:376`

```python
while len(out) < n:
    if not workday_only or d.weekday() < 5:
        out.append(d.isoformat())
    d += timedelta(days=step)
```

**失败场景**：`{"start":"2026-10-31","count":5,"step":7,"workdays_only":true}`。10-31 是周六，`weekday()==5` 永远不满足，`out` 永不增长，`while` 永不退出 —— 同步 worker 被**永久**占死（比 OOM 更难恢复，OOM 至少会崩）。

**修复**：入口阻断 + 循环上限双保险。

```python
if workday_only and step % 7 == 0:
    raise ValueError("step 为 7 的倍数时无法保证取到工作日")
for _ in range(max(1, n) * 7 + 14):        # 硬上限
    if len(out) >= n:
        break
    ...
```

## 七、验证期间发现并修复的附加问题

### 附加-1 SQLite 排序依赖磁盘临时文件，导出接口在受限环境 500 ✅已修复

**位置**：`backend/core/apps.py:32-44`

**现象**：冒烟测试「日志导出CSV」失败，接口返回 500 `unable to open database file`，但同一接口的 `count()` 正常。

**根因**：`OperationLog.Meta.ordering = ["-created_at"]`，导出 `[:10000]` 需要在 2.2 万行上排序。SQLite 默认 `temp_store=FILE`，排序临时文件走系统 Temp；本机系统 Temp 被安全软件管控（写不进去）→ 打不开临时文件。**在生产容器（只读 rootfs、无 /tmp）或安全加固环境下同样会触发**。

**修复**：

```python
cur.execute("PRAGMA synchronous=NORMAL")
cur.execute("PRAGMA temp_store=MEMORY")   # 排序/临时表放内存
```

**验证**：修复后冒烟 161 项全绿；本项目 SQLite 规模（库 7.3MB）内存排序代价可忽略。
